Caos de Integrações Manuais

  • ✕
    Teia de Conexões Ponto a Ponto: Cada aplicação precisa conhecer os IPs e URLs físicas de cada serviço. Se uma rota mudar, o sistema quebra.

    Barreira Gigante para IA: Modelos de linguagem (LLMs) não conseguem conversar com segurança em dezenas de APIs sem regras centralizadas.

        📖 PARTE 1: Explicação Conceitual (Aprenda de uma vez por todas)
      


      

        
        
        

          

            🔌 Como funciona a comunicação básica (Conexão Única)
          

          
          

            
            

              
Explicação Técnica e Profissional

              

                O INP funciona sob a arquitetura de Service Registry (Catálogo de APIs). Cada microsserviço (ex: serviço de cobrança) expõe uma lista de capacidades lógicas (ex: EXECUTE PAYMENT). O cliente submete a requisição para o Gateway (Porta 3000). O Gateway atua como um roteador dinâmico: ele localiza o serviço ativo no catálogo de microsserviços e encaminha a requisição via chamada HTTP transparente, eliminando a necessidade do cliente saber o IP ou porta de cada microsserviço diretamente.
              

            

            
            
            

              
Modo Didático (Até uma criança entende 🧸)

              

                Imagine que o Gateway é uma secretária super inteligente em uma agência de ajuda. Você (o cliente) entra na agência e apenas diz: "Quero que limpem minha casa!". Você não sabe quem limpa casas e nem onde os faxineiros moram. A secretária consulta o caderninho dela (o catálogo), vê que o João (o microsserviço) sabe limpar casas, e ela mesma liga para o João pedindo para ele ir fazer a faxina. Você só fala com a secretária e tudo acontece magicamente!
              

            

          

        


        
        

          

            ⛓️ Como funciona a Orquestração Distribuída (Múltiplos Microsserviços)
          

          
          

            
            

              
Explicação Técnica e Profissional

              

                Para conectar múltiplos microsserviços, a DSL compila uma Árvore de Sintaxe Abstrata (AST) contendo regras de controle. Em fluxos SEQUENCE, o Gateway gerencia o encadeamento e a propagação de variáveis de estado entre microsserviços. Em fluxos PARALLEL, o motor gerencia o sincronismo assíncrono (Promise.all) otimizando a latência do lote de requisições. As políticas de resiliência (RETRY e TIMEOUT) atuam como guardas de rede, interceptando falhas (ex: HTTP 500, timeouts) e re-executando chamadas automaticamente sem necessidade de lógica customizada no código da aplicação.
              

            

            
            
            

              
Modo Didático (Até uma criança entende 🧸)

              

                Fazer múltiplos microsserviços trabalharem juntos é como seguir uma receita de bolo de aniversário. A receita diz os passos organizados (SEQUENCE): Passo 1: Assar a massa, Passo 2: Fazer o recheio de morango, Passo 3: Colocar o recheio sobre a massa. Se o ajudante derramar o recheio no chão, a receita diz para ele tentar de novo até 3 vezes (RETRY). Se a massa demorar mais de 10 minutos para assar, ele desiste e desliga o forno para não queimar (TIMEOUT). Tudo isso está escrito na receita, e o cozinheiro faz tudo sozinho!

1. Introdução & Conceitos

            
O Intent Network Protocol (INP) é uma infraestrutura de orquestração distribuída projetada para desacoplar as chamadas entre clientes e microsserviços. Em abordagens tradicionais (REST, RPC), o cliente precisa conhecer os caminhos físicos dos endpoints de API, as regras de retry e os formatos exatos de payload.

            
Com o INP, o cliente fornece uma Intenção (Intent). Uma intenção descreve o objetivo da operação em um formato declarativo (DSL) ou em linguagem natural estruturada. O gateway INP resolve dinamicamente as capacidades exigidas no catálogo de serviços cadastrados, valida os contratos por JSON Schema, aplica regras de segurança baseadas em permissões (RBAC) e orquestra a execução de forma resiliente.

            

              
Diferencial Técnico: O INP remove o ponto único de falha lógica nos fluxos de microsserviços e simplifica a integração de IA ao permitir que as LLMs tomem decisões de roteamento a partir das capacidades registradas.

            

          


          
          

            
2. Visão da Arquitetura

            
O funcionamento do ecossistema INP é dividido em cinco componentes principais:

            
    
              
  • INPCore: Ponto de entrada que centraliza a execução e coordena as chamadas entre os submódulos.
    • 
              
  • IntentParser: Analisador sintático da DSL estruturada que gera uma representação abstrata da árvore de execução. Se configurado com IA, o hook aciona o modelo de linguagem para mapear sentenças informais de usuários.
    • 
              
  • CapabilityRegistry: Catálogo mantido no PostgreSQL com cache local em memória (RegistryCache) de microsserviços ativos que anunciam capacidades específicas.
    • 
              
  • ExecutionEngine: Motor recursivo responsável por navegar no grafo, avaliar condições, tratar encriptações de dados do contexto, monitorar timeouts e realizar as chamadas HTTP.
    • 
              
  • ResponseComposer: Transforma o resultado final da execução em formatos estruturados solicitados pelo cliente (JSON, XML, Plain Text ou SSE).
    • 
            

          


          
          

            
3. Guia de Setup Local

            
Para implantar o INP Protocol no ambiente local, certifique-se de ter instalado o Node.js v18+ e o PostgreSQL.

            
1. Instale as dependências na pasta raiz do projeto:

            
npm install

            
2. Crie e configure o arquivo .env copiando os valores de exemplo. Ajuste os dados de conexão do banco de dados:

            
PORT=3000
DATABASE_URL=postgres://inp:inp123@localhost:5432/inp
GEMINI_API_KEY=sua_chave_gemini_opcional

            
3. Inicialize o servidor em modo de desenvolvimento:

            
npm run dev

            
4. Em outro terminal, inicie o microsserviço mock de pagamentos para simular chamadas de rede:

            
npm run mock-service

          


          
          

            
4. Especificações da DSL

            
A Domain Specific Language (DSL) do INP permite desenhar fluxos transacionais complexos com poucas linhas de código:

            
INTENT "nome_da_intencao" {
  CONTEXT {
    user_id: "usr_1",
    amount: 150.00
  }
  REQUIRE {
    EXECUTE PAYMENT
  }
  FLOW {
    SEQUENCE {
      EXECUTE PAYMENT
    }
  }
  OUTPUT {
    FORMAT "json"
  }
}

            
O bloco CONTEXT carrega as variáveis de entrada. O bloco REQUIRE lista os verbos obrigatórios que devem constar no gateway para o fluxo iniciar. O bloco FLOW define o algoritmo de orquestração das capacidades.

          


          
          

            
5. Segurança & RBAC

            
As capacidades dos microsserviços declaram permissões obrigatórias no atributo requiredPermissions durante o registro. Ao executar uma intenção, o cliente deve fornecer as credenciais do usuário através do objeto securityContext:

            
{
  "securityContext": {
    "userId": "usr_77",
    "permissions": ["payments.write"]
  }
}

            
O ExecutionEngine realiza uma validação rigorosa em tempo de execução. Se alguma capacidade do grafo exigir uma permissão não incluída na lista do usuário, o passo falha imediatamente e uma exceção de violação de segurança (Security Violation) é disparada.

          


          
          

            
6. Validação de Contratos

            
Para evitar chamadas de APIs com payloads incompletos, o catálogo aceita especificações de JSON Schema vinculadas a cada capacidade. No momento em que uma ação é disparada, o motor de execução compila as regras do schema via biblioteca Ajv e valida as chaves correspondentes no contexto local.

            
Se o validador encontrar inconsistências (tipos de dados errados, falta de chaves obrigatórias), a chamada HTTP não é efetuada, prevenindo desperdício de recursos computacionais nas redes corporativas.

          


          
          

            
7. Políticas de Resiliência

            
O INP vem equipado com padrões industriais de resiliência activa:

            
    
              
  • Retries com Backoff Exponencial: Configurado em requisições via axios-retry. Tenta restabelecer chamadas falhas aplicando intervalos de atraso que crescem exponencialmente para proteger serviços sobrecarregados.
    • 
              
  • Circuit Breaker: Gerenciado localmente. Se a taxa de erros de conexão com determinado microsserviço atingir 50% de erro em uma janela deslizante de tempo, o circuito "abre", falhando instantaneamente requisições subsequentes sem gerar requisições de rede físicas.

9. Padrão Saga & Rollback

            
O INP implementa o padrão **Saga Orquestrado** para gerenciar transações distribuídas entre microsserviços. Toda capacidade que define uma compensação (compensateCapability) registra de forma reversível a ação correspondente na tabela saga_states em formato LIFO.

            
Caso ocorra uma falha irrecuperável e a política for ROLLBACK, o gateway reverte cada ação concluída, garantindo consistência eventual. Na inicialização do servidor, o SagaRecoveryManager busca por transações pendentes/interrompidas para concluir suas compensações automaticamente.

            

              
Bypass de RBAC: Durante o processo de compensação automática do sistema, as validações de permissões do usuário (RBAC) são temporariamente ignoradas (modo de rollback) visto que a ação roda sob o contexto do orquestrador.

            

          


          
          

            
10. Fila & Outbox (SKIP LOCKED)

            
Para fluxos assíncronos de alta escalabilidade, o INP suporta o Transactional Outbox Pattern. Ao enviar um payload com async: true na API, o job de execução é enfileirado na tabela queue_jobs de forma transacional e uma resposta rápida com status PENDING é retornada imediatamente.

            
O QueueWorker escuta em segundo plano e processa os jobs pendentes de forma segura. Para evitar colisões e concorrência indesejada entre múltiplos gateways activos na rede, o worker adquire travas pessimistas usando a instrução SKIP LOCKED do PostgreSQL (.setOnLocked('skip_locked') no TypeORM).

            

              
NOWAIT Lock: De maneira similar, travas pessimistas imediatas do tipo FOR UPDATE NOWAIT são utilizadas nas Sagas em rollback para impedir que dois servidores paralelos tentem reverter a mesma transação simultaneamente.

            

          


          
          

            
11. SafeEvaluator & Criptografia

            
O INP preza pela segurança em nível empresarial através de dois submódulos:

            
    
              
  • SafeEvaluator: Um analisador sintático completo baseado em AST (Árvore de Sintaxe Abstrata) construído com Parser de Descida Recursiva. Ele substitui eval() nas etapas de CONDITION, permitindo avaliar condições lógicas/matemáticas (ex: context.amount > 100) de forma blindada contra injeção de código arbítrio.
    • 
              
  • Criptografia com Rotação (CryptoEngine): Fornece encriptação simétrica forte usando o algoritmo aes-256-gcm. Suporta rotação de chaves baseada em versão de prefixo (ex: v2:iv:authTag:cipherText), mantendo compatibilidade reversa para ler dados antigos enquanto criptografa novas entradas usando a chave activa mais recente.
    • 
            

          

        

      

    


    
    

      
Perguntas Frequentes & Central de Ajuda


      

        

          

            Como funciona o catálogo de capacidades e o cache em memória?
            ▼
          

          

            O CapabilityRegistry lê os microsserviços do banco PostgreSQL. Para maximizar a velocidade, o sistema implementa um cache em memória (RegistryCache) que armazena os dados dos serviços com um Time-To-Live (TTL) de 30 segundos. Alterações no catálogo (novos cadastros de microsserviços ou heartbeats inativos) invalidam o cache imediatamente.
          

        


        

          

            O que acontece se uma chamada de microsserviço falhar no meio do fluxo?
            ▼
          

          

            O motor de fluxo (ExecutionEngine) interrompe a execução do bloco atual e busca um passo com a diretiva FALLBACK configurada. Caso não haja tratador de fallback mapeado, a transação é encerrada e persistida no banco PostgreSQL com o status "FAILED", acompanhada do log detalhado e do stack do erro.
          

        


        

          

            Como configurar chaves de Inteligência Artificial para linguagem natural?
            ▼
          

          

            Para ativar a conversão inteligente de linguagem natural com LLMs reais, adicione uma chave de API válida GEMINI_API_KEY ou OPENAI_API_KEY no arquivo .env. Se nenhuma chave for fornecida, o sistema aplica um parser heurístico via expressões regulares (regex) como plano de contingência transparente.
          

        


        

          

            Onde posso depurar violações de contratos de JSON Schema?
            ▼
          

          

            Toda violação de contrato gera um erro explicativo no resultado da orquestração. No Playground do painel, você verá a tag "FAILED" no passo correspondente e a caixa de logs de API mostrará exatamente qual campo violou o JSON Schema do serviço (ex: valor abaixo do mínimo exigido ou chave obrigatória ausente).
          

        

      


      

        
🛠 Guia de Resolução de Problemas (Troubleshooting)

        
    
          
  • Erro: listen EADDRINUSE :::3000 - Outro processo Node está utilizando a porta 3000. Finalize-o no terminal usando npx kill-port 3000 antes de executar `npm run dev` novamente.
    • 
          
  • DB: Offline no Cabeçalho - Verifique se o serviço do banco de dados PostgreSQL está ativo no sistema local e se as credenciais cadastradas no arquivo .env coincidem.
    • 
          
  • Contratos não validam - Certifique-se de que os dados de entrada na aba Playground possuem as mesmas chaves configuradas nos schemas declarados pelos microsserviços.
